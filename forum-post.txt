Suggested title:
TREX - a CPU + DSP benchmark for the Falcon, stock or accelerated
(with a dinosaur attached)

----------------------------------------------------------------------

Hi all,

I have been porting the T-Rex sequence from the PlayStation "Demo One"
disc (SCES-00048) to the Falcon030. The release build turned into
something I did not plan for: a repeatable load that leans on the 68030
and the DSP56001 at the same time, with the frame rate printed on
screen. If you own a CT2, CT60/CT63, an AfterBurner040, a DSP clock mod
or anything else that changes one of those two numbers, I would like to
know what it does to this.

It needs none of that hardware, though. A stock 16 MHz Falcon030 runs it
as it is - that is the machine it was written and tuned on - and right
now a stock result is the number I want most, because there is no
measurement from any real Falcon at all yet. Someone has to set the zero
point before the accelerated figures mean anything.


WHAT IT IS

The original PS1 model, morph animation and texture pages, extracted and
rebuilt for the Falcon. Everything that moves and draws them is new
Falcon code.

  * 1376 vertices, 2724 triangles, full detail, every frame - no
    reduced model, no dropped geometry
  * DSP56001: pose morph, transform, projection, near plane / back face
    / area / screen culling, per corner Gouraud lighting, span setup,
    and a screen space occlusion prepass that kills hidden triangles
    before they ever reach the host
  * 68030: packet build, ordering table, and a textured Gouraud span
    rasterizer in painter's order, no Z buffer
  * 240x224 true colour inside a 256x224 Videl mode, programmed by
    register, double buffered and page flipped, RGB/TV and VGA both
    scanning all 224 lines
  * Frame rate top left as NN.NN, measured over the frame you are
    looking at, fixed width so the digits never jump


WHY IT BENCHMARKS BOTH SIDES

The frame is genuinely split across the two processors:

  CPU, bus and caches   packet build, ordering table, span walk,
                        pixel loops
  DSP                   morph, transform, projection, culling,
                        lighting, span setup
  Host port PIO         the traffic between them, which scales with
                        neither one on its own

On a stock 16 MHz Falcon under Hatari that comes out at roughly 40% DSP
readback plus packet build, a little over half in the rasterizer, and
the rest in frame setup - about 2.3 fps. A faster CPU should shrink the
raster half and push the frame towards being DSP and transport bound.
Where that crossover actually lands is exactly what I cannot measure
from here.


WHY THE NUMBERS ARE COMPARABLE

The workload is fixed: same 274 frames of authored choreography, same
mesh, same textures, no input, no random element, no disk access, no
frame skipping and no timing dependent shortcuts. Stock against stock,
one accelerator against another, or the two against each other - the
readout means the same thing in every case. Two phases:

  1. Frames 0 to 273, the flyby, with occlusion culling armed. The
     camera moves and the on screen area changes, so the readout moves
     with it.

  2. Afterwards the walk cycle and a slow turn continue with culling
     switched off, so the full 2724 triangles are drawn every frame.
     Heavier and much steadier - that is the better single number to
     quote.


HOW TO RUN IT

Falcon030 with a working DSP, 4 MB RAM (it needs about 3 MB and lives in
ST RAM only), TOS 4.0x, RGB/TV or VGA.

Unpack the archive and start TREX.TOS from its own folder - it loads
TREX.LOD out of the current directory. Any key quits, the video mode is
restored on exit, and nothing is written to disk.


WHAT TO POST

  * machine, stock or accelerated, CPU type and clock, DSP clock if
    modified
  * RAM configuration, TOS version, monitor type
  * the steady rate during the walk phase, plus roughly the low and
    high you see during the flyby
  * a photo or screen shot if anything looks wrong


CAVEATS, UP FRONT

Everything measured so far is Hatari, not hardware. There is no physical
Falcon030 baseline yet - whoever posts the first one gives this thing
its zero point.

The code is assembled for the 68030. It stays clear of the instructions
the 68040 and 68060 dropped (no MOVEP, no 64 bit MULS/DIVS), but it has
never been run on an accelerated machine, it programs the Videl
registers directly and it runs in supervisor mode throughout. If it
misbehaves on your setup that is useful data as well - please say what
you saw.

And no, it is not fast on a stock machine, but it does run there and it
runs correctly there. 2724 software rasterized triangles per frame at
16 MHz is a slide show by construction. That is the point: there is a
lot of headroom in it for a faster machine to show off with, and a
stock reading to measure that headroom against.

Source, build instructions and the full optimization log (every measured
step, including the ones that were rejected) are here:

  github.com/AnimaInCorpore/F030TREX

CREDITS, and one part of them worth stating plainly: the PlayStation
forensics - working out the model, the morph animation and the texture
pages from the disc - the entire 68030 side and most of the DSP side were
written by AI: ChatGPT 5.6, Claude Opus 5 and Claude Fable 5. I would
rather say that up front than have someone find it out later.

My own share is the direction, a number of the ideas, and exactly two
routines - but they are the two the whole thing turns on. The per vertex
transform and the perspective divide running on the DSP are lifted from
the Falcon DSP 3D engine I wrote in 1994. The MAC pipeline is unchanged
apart from three rounding instructions, and it executes 1376 times per
frame. Thirty-two years later the oldest code in the project is still the
hottest loop in it, which I did not expect when I started this.

Model, animation and textures are from Sony's "Demo One" (SCES-00048).
The 256x224 Videl register sets come from Screenspain (Chris/AURA and
Scandion/Mugwumps) via the F030Arcade snowbros port. Non commercial
hobby port.
